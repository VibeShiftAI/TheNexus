## 1. Summary

The refreshes were full browser reloads forced by the live dashboard's development server. The live cockpit on :3000 is a hot-reloading `next dev` serving the working tree, and at 15:02 EDT the Praxis executor for task a10da6d9 ("Add collapse/expand pip to Voice/Start Conversation bar") began saving `dashboard/src/components/global-voice-dock.tsx`, a module the root layout imports. That commit (`ebf0e42`) added a plain constant export to the module, which disqualifies it as a React Fast Refresh boundary, so every save of the file reloaded every open dashboard tab. The review page keeps the comment being typed only in React state, so each reload erased it.

No durable record of the "deleted saved comment" was found in the inspected evidence. The database holds no review, comment or decision for that document by any reviewer, the write-ahead log holds none, comment rowids are contiguous, and comments are only hard-deleted through an explicit Delete action. That is the absence of a record in what could be inspected, not proof that no save or deletion ever occurred: SQLite keeps no deleted rows, contiguous rowids do not rule out the deletion of a last-inserted row, and the write-ahead log only holds frames written since its last reset. The most likely reading is that the reload interrupted the Save click before the server acknowledged it, and the page then showed nothing because there was nothing stored. The wording of both lost comments is unrecoverable from the inspected evidence: no server record exists and the page had no browser-side draft storage.

The fix has three parts, all in this tree: unsaved review text (comment, reply, edit, summary) now persists in the browser bound to the document, revision and reviewer and comes back after a reload; a read that overlaps a save can no longer replace the review with an older copy; and the voice dock module is a refresh boundary again, with a test that keeps every layout-imported module that way. The dashboard parts are live through hot reload. The two small API additions (`viewer` on the document read, `client_id` on review comments) wait for the next restart of :4000 and the page tolerates their absence.

## 5. The fix

### 5.1 Unsaved review text survives a reload (dashboard, live)

- `dashboard/src/lib/review-drafts.ts` (new): stores one draft record per document under `nexus:document-review-draft:<document id>` in localStorage, with sessionStorage as the fallback when the first store refuses. The record carries the document id, the revision on screen, the reviewer the API served, the open review id, the composer (client id, kind, anchor, quote, selection, parent, text), the comment edit (comment id, the body the edit started from, text), the summary (text and the server summary it was typed over) and any recovered passages. Records older than fourteen days are ignored. `reconcileReviewDraft` is a pure decision: restore, keep as recovered text, treat as already saved, or ignore as foreign.
- `dashboard/src/components/document-review/document-review.tsx`: writes the record on every change to the composer, edit box or summary, but only after the stored draft for the current document has been reconciled, so the empty initial state can never wipe a draft. After the first read of a document it restores: a composer goes back exactly where it was (same block, quote, selection, anchor, parent, client id) with a visible "Restored from this browser after the page reloaded; not saved until you save it" line; an edit reopens on its comment; a restored summary shows a notice with "Save now" and is not saved until the reader acts. Saving, cancelling, finishing or discarding clears the record.
- Binding rules, in order: another document or another known reviewer is left alone; a comment whose save already landed, proven only by its own client id on a saved comment, is dropped as done (wording never discards a draft: the first QA round showed "Please clarify." saved on lines 7-8 swallowing the same words typed on line 3, repaired in the second round); a finished review, a reply whose parent is gone, an anchored comment written for another revision, or an edit of a comment that changed elsewhere becomes recovered text in an amber card with "Use as a note about the whole document", "Copy" and "Discard". Recovered text is never re-anchored, never saved on its own, and survives further reloads until the reader acts.
- Until :4000 restarts, the API reports no client ids, so a landed save cannot be confirmed: the draft is kept, and when a saved comment with the same text sits at the same place the restored composer says so ("cancel this draft if it is the same one"). Saving the kept draft again is idempotent, since the server dedupes on the client id it stored, so the worst case is a redundant composer, never a lost comment.
- The page resets review, submission, composer, edit, summary, selection and the pending summary save when its document id changes, and `dashboard/src/app/documents/[id]/page.tsx` now keys the reviewer by document id.

### 5.2 A stale read cannot hide a saved comment (dashboard, live)

`load()` records a write sequence before its request. Applying a comment, removing one, saving the summary, opening a review or finishing a review bumps the sequence, and a read that started before any of them no longer replaces the review with its older copy. The idempotent save path is unchanged: a retry after a failure or a reload reuses the client id minted when the composer opened, and the server dedupes on it.

### 5.3 The dev server stops reloading every tab for that file (dashboard, live)

`VOICE_DOCK_COLLAPSED_KEY` moved to `dashboard/src/lib/voice-dock-preferences.ts`; `global-voice-dock.tsx` imports it and exports only the component. `dashboard/src/lib/__tests__/fast-refresh-boundaries.test.ts` reads the root layout's component imports and fails if any of them gains a non-component export, with the four modules that already have them listed as the known exceptions (`bridge/activity-provider`, `cortex-provider`, `live-board-state`, `connection-banner`).

### 5.4 API additions (server, not live until :4000 restarts)

`GET /api/documents/:id` now returns `viewer: { id }`, the reviewer the read is for, and the review view carries each comment's `client_id`. The page binds drafts to the viewer when present and confirms a landed save by client id when the API reports them; without them it binds by document and revision only, keeps every draft, and points out a same-text comment at the same place. The Praxis feedback payload is unchanged (`publicComment` in `server/services/document-review-format.js` was not touched).

## 8. Remaining risks and follow-ups

1. Praxis dependency (not changed here): executors edit the same working tree the live cockpit hot-reloads. Any save of `bridge/activity-provider`, `cortex-provider`, `live-board-state` or `connection-banner` still reloads every open tab, because those modules export hooks and constants alongside components. Either move those exports to lib modules (the ratchet test lists them and will shrink as they are fixed), or have the supervisor serve :3000 from a build (`PRAXIS_DASHBOARD_DEV` unset) while executors work. That is a supervisor and dispatch policy decision for Praxis, so it is recorded here rather than made.
2. Drafts live in the browser that typed them. A different device or a cleared browser profile cannot restore them; the server still only stores what "Save comment" acknowledges.
3. A summary cleared to empty and not yet autosaved is not kept across a reload (the record treats empty text as no draft); the previous server copy returns.
4. The recovered-text card is per document and capped at eight entries; older entries drop first.
5. Until :4000 restarts, a reload that lands during a save brings the draft back next to the comment it already created, with a note that a saved comment with the same text is at the same place; the reader cancels it, or saves again and the server dedupes. After the restart the client id confirms the save and the draft is dropped.
