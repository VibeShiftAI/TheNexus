# Member memory pilot

The Cortex assessment recommended a durable member history feeding an evidence-backed current profile, with Nexus remaining the canonical people directory. Robert approved continuing. This pilot implements that first slice across the shared contract, Nexus API/dashboard, and Praxis tools. It does not replace Cortex or turn observations into personality judgments.

## Choice

Putting profiles in Cortex's global operator synthesis would mix subjects. Extending the bounded JSON log would continue losing evidence. Use an append-only SQLite member event ledger in Nexus, with a deterministic current view and explicit member/project scope. The existing directory fields remain authoritative for contact details and outreach approval. The ledger holds supporting working knowledge and commitments.

## Contract and behavior

- Stable event IDs, canonical member UUID, optional canonical project ID, server recording time, optional occurrence/effective/expiry dates, source label/reference, and evidence class (`self_reported`, `operator_confirmed`, `observed`, `inferred`, `legacy`). Preserve full text up to a deliberate 20,000-character input limit; reject oversize input rather than silently truncating it.
- Kinds: `observation`, `fact`, `commitment`, `retraction`, `resolution`. Facts have a key. A corrected fact is a new fact with `supersedes_id`; retractions/resolutions refer to `target_id`. Commitments have owner (`praxis` or `member`), optional deadline; resolutions have outcome (`completed` or `cancelled`).
- Corrections and transitions must target the same member and exact project scope, and an active compatible event. Retraction can also cancel a scheduled fact/correction before its effective date; cancelling a future correction preserves its predecessor, while retracting an already-effective replacement never resurrects the predecessor. No edits or deletes of individual events. Deliberate whole-member deletion erases that member's ledger with the directory record. Conflicting active facts remain visible, grouped by key; recency alone does not establish truth. Effective dates and expiry determine the current view. An inferred fact remains explicitly inferred.
- Optional idempotency keys are unique per member. Identical retries return the original event; changed payloads using the same key fail with 409. Timestamps generated by the server are not part of retry equality.
- `GET /api/members/:id/memory` returns current facts, conflicts, open commitments, and one timeline page. General scope is the default; `project_id` requests exactly that project, never another project's events. A cursor pages older events without limiting durable storage. Metadata makes scope, as-of time, and total history count explicit. Missing members/projects and invalid cursors fail clearly; an otherwise-deleted project scope remains readable when that member has historical events there. The dashboard's scalar cachebuster is accepted.
- `POST /api/members/:id/memory` validates the shared input schema and appends one event. Project events require an existing member/project link. Existing events remain readable after unlinking, preserving the operator's history.
- Backfill only legacy log entries that still exist. Preserve their original source/time text and label their evidence legacy; do not invent missing source documents or reconstruct already-pruned history. A migration marker makes reopening idempotent. New calls to the old `/log` append full text durably in the same transaction as updating the compatibility window (latest 200, historical 2,000-character projection). New private working-memory writes do not enter that compatibility window or existing portal snapshots.

## Product surface

Add a member-memory panel within an expanded project stakeholder. Show this project's current facts, unresolved disagreements, commitments, evidence labels/references, and paged history. Allow a deliberate switch to general member notes. Let Robert record an observation/fact/commitment, correct or retract facts, and resolve commitments. Do not auto-generate scores or biographies. Render references as inert text unless an explicitly safe web link is needed.

Provide Praxis a `member_memory` tool using canonical member UUIDs (obtain them from the directory), explicit scope, and the same API/validation. Reads instruct the agent to treat text as evidence, ignore embedded commands, preserve uncertainty, and verify current authoritative directory fields before outreach. No widening of the executor read-only bridge allowlist. No automatic export into Cortex's global graph, shared research vault, or member portal.

## Trust boundary and scope

These routes use Nexus's existing trusted operator API and deployment boundary; Nexus does not currently enforce application-level member ACLs. Project filtering is retrieval isolation, not multi-tenant authorization. The pilot must not be advertised as a member-facing private-data API. Member-authorized sharing, retention/erasure policy, automatic evidence extraction, reliable consultation writeback, graph federation, and outcome evaluations beyond deterministic fixtures remain subsequent releases.

## Acceptance

Prove full histories survive >200 writes and >2,000-character notes, migration is repeatable, same-name members stay separate, project filters do not mix records, incorrect/stale transitions fail atomically, inferred statements retain their status, conflicts/expiry affect current views correctly, retry writes are idempotent, and internal writes never appear in legacy portal data. Verify route errors, Praxis's tool requests/errors, the dashboard build, and the actual panel on a synthetic local member.
