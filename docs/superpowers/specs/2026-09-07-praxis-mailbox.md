# Dedicated Praxis Inbox and Outbox

Robert explicitly requested a separate Inbox/Outbox for the Praxis email address, opened by clicking its dashboard pip. This replaces the proposed use of the task approval Inbox for incoming consulting messages. Website-to-Praxis inquiry transport remains a separate follow-up; this feature exposes the existing Praxis mailbox.

The COMMS pip opens `/mail` inside the dashboard. This dedicated mail page has Inbox and Outbox tabs, a list and full-message reader, sender/recipient/date metadata, loading/error/empty states, and pagination. Outbox has Pending and Sent filters: Pending shows existing Praxis human-query drafts with their current approval state and a link to the existing approval card; Sent reads the actual mailbox's Sent folder. Robert subsequently selected a combined Inbox with All, Email, and Feedback filters. Email reads actual INBOX including seen messages. Feedback opens the original submission, related Praxis responses, replies and questionnaire answers, and linked work as a plain-text conversation. Standalone Praxis questions and answers are included by trace tag. This replaces the old summary-only Feedback activity modal entry.

Use the configured dedicated PRAXIS_EMAIL_USER/PASSWORD and IMAP host/port. Never fall back to Robert's personal Gmail. The API is read-only: inspecting mail does not mark it seen, delete/move messages, send anything, invoke a model, or restart workers. Bodies render as plain text; do not load remote mail images or execute HTML. Attachments show metadata only. This scope does not add a composer or change approval/send policy.

Praxis serves GET `/api/mailbox?folder=inbox|sent|pending&cursor=...&limit=30` and GET `/api/mailbox/:folder/:id`. Nexus exposes matching GET proxies at `/api/praxis/mailbox...`, preserving existing API authentication. List response: `{ account, folder, items, nextCursor, updatedAt }`. Each item has `{ id, subject, from, to: string[], date: string|null, status, unread?, approvalId?, approvalState? }`. Status is `received`, `sent`, or `pending`; approvalState may distinguish approval pending, queued, cancelled, expired. Detail adds `{ body, cc: string[], replyTo: string[], messageId?, attachments: [{ filename, contentType, size }], bodyUnavailable? }`. Backend validates folders/cursors/IDs, uses stable UIDVALIDITY+UID identifiers for real mail, bounded metadata batches, a bounded detail size, safe generic service errors, and closes connections after each request. `account` is the configured dedicated mailbox, not a new account.

The clarified API adds folder=all|feedback. Summaries add source, tag and project where available. Feedback detail adds thread metadata and chronological entries with direction, kind, date, sender/recipients, body, status, approval link and attachment metadata. The DTO excludes questionnaire capability tokens. Large threads explicitly indicate omitted history/text. Reading existing records starts no ingestion or planning. All uses bounded merging of source prefixes; its composite cursor advances only past consumed entries. Mail order follows UID arrival order, so old imported email dates can appear out of chronological order.

The frontend does not imply zero messages on a failed fetch. A source failure explicitly fails the combined list while separate filters remain available. It clears stale selection when switching folders, prevents a late detail response replacing a newer selection, and paginates without skipping unconsumed mail or threads. The COMMS pip links to the mail page; its old mixed-feedback counts must not be presented as email counts.
