# Markdown document review with feedback to Praxis

Robert asked for a proper way to review Markdown files that tasks produce: open the actual file in a full-format viewer on desktop or phone, comment on passages and on the document as a whole, and have the finished review reach Praxis in his existing persistent chat. The first document is the Praxis reliability readiness report of 2026-09-10 (`/Volumes/Projects/Praxis/docs/reports/2026-09-10-reliability-readiness.md`, source task `6f6017f3-a752-417f-a3a7-28602892c4f2`).

## Shape

One review model, one API, one shared page. The Nexus API owns a **document registry** (server-issued ids bound to canonical paths inside registered project roots), **content revisions** (immutable snapshots keyed by SHA-256), **reviews** (one open draft per reviewer per document, pinned to a revision), **comments** (passage or whole-document, with quoted source text and line anchors verified against the pinned revision) and **submissions** (the durable outbox that delivers a finished review into the Praxis conversation). The dashboard renders `/documents/<id>`; the task page lists a task's registered documents with a "Review document" link. The existing `MarkdownReviewer` (line-by-line, used by the nexus-builder artifact panel) and `AnnotatedMarkdown` (stage-bound inline comments) stay as they are; this feature adds the full-file review lifecycle they lack rather than a third incompatible comment store for the same surfaces: the artifact panel's `/api/artifacts/:id/comments` routes do not exist in this API, so nothing is migrated.

## Document registry and reading

`POST /api/documents` registers `{ path, title?, project_id?, task_id?, kind?, metadata? }`. The server resolves the real path, requires it to lie inside the real path of a registered project (`projects.path`), requires a `.md`/`.markdown` extension on both the given and the resolved path, rejects `.git` and `node_modules` segments and files over 2 MB, and stores the canonical path. A symlink that resolves outside every project root is refused; a path that resolves inside a root is stored by its resolved form. Registration is idempotent on canonical path plus task: re-registering returns the existing document and refreshes title/associations. Executors and Praxis register documents with curl; nothing serves an arbitrary local file.

`GET /api/documents/:id` re-checks the boundary, reads the file, normalizes line endings, hashes it and captures a new revision row when the hash changed, then returns the document, its current revision and content, the source task/project summary, and the caller's review (draft or submitted) if one exists. `GET /api/documents/:id/raw?revision=` serves the Markdown source as a download; `GET /api/documents/:id/revisions/:revisionId` serves a pinned snapshot. `GET /api/documents?task_id=` lists a task's documents for the task page. All `/api/documents` routes sit behind the existing `authenticate` middleware and are reached through the dashboard `/api` proxy (and the Cloudflare `/api/*` ingress on the phone), so the deep link `https://nexus.vibeshiftai.com/documents/<id>` works wherever the dashboard does.

Rendering is react-markdown with remark-gfm on the exact stored content (no normalization, so remark line positions match the stored lines). A small rehype step stamps every top-level block with its source line range; the renderer wraps those blocks with an explicit comment control that is always visible on coarse pointers and appears on hover/focus on desktop. Raw HTML is shown as text, never rendered, and react-markdown's default URL transform strips `javascript:`/`data:` targets; links open in a new tab with `rel="noopener noreferrer"`. The page shows title, source task and project, revision hash and capture time, the task's live status line, a heading outline, and source/download controls.

## Anchors and revision pinning

A passage comment stores `start_line`, `end_line`, the exact quoted block source (`quote`) and, optionally, the selected sub-text. The server accepts a passage comment only when the quote equals those lines of the review's pinned revision and records the block hash itself; the client never fabricates an anchor the server cannot verify. A review is pinned to the revision it was opened on. When the file changes, the API keeps serving the pinned snapshot for that review, reports `document_changed`, and marks each passage comment `intact` (quote still present in the current revision), `moved` (present at a different line) or `orphaned` (absent). Anchors are never relocated silently; the reviewed snapshot remains available for download.

## Drafts, saving and finishing

Comments and the summary save to the server as they are entered; the sidebar shows saving / saved / save failed with retry, and a failed save keeps the text in the composer. Comment creation carries a client id so a retried request cannot duplicate a comment. A storage fault during a save answers 500 and leaves everything saved before it intact. A draft survives refresh and other clients because everything is server state. On the phone the review drawer closes while a whole-document note is composed, so the composer sheet is the topmost surface under the reviewer's finger, and it reopens when the note is saved or cancelled. "Finish review" (optional summary, zero comments allowed) freezes the review, writes one submission row per review (repeat finishes return the same submission) inside one transaction, and leaves the document untouched; a fault inside that transaction rolls the status change back, so the review stays a draft with its comments and no submission or delivery exists. If the Finish request fails in transit, the page reconciles with the server before saying anything: a review the server shows as submitted is adopted with its submission state, a review still in draft is reported as "nothing was sent; your draft is intact", and an unreachable server is reported as unconfirmed with a reload instruction. The submission payload snapshots every comment verbatim with its anchor and quote, the summary, the document title, path, revision hash, source task/project and the exact review URL.

## Delivery into the Praxis conversation

Delivery reuses the canonical Nexus-to-Praxis chat seam: the same `praxisFetch('/api/chat')` relay and the same `chat_conversations`/`chat_messages` persistence the bridge chat uses, so the review lands in Robert's active Praxis conversation as his own turn and Praxis answers in place. The outbox worker (`server/services/document-review-delivery.js`) persists the user turn under the deterministic id `docreview:<submissionId>`, relays the formatted review (verbatim comments, no summarization) to Praxis, stores the reply under `docreview:<submissionId>:reply`, emits the usual `chat-message` socket events, and records a receipt (conversation, message ids, time). Duplicate suppression is durable on both sides of the seam: a stored reply marks the submission delivered without a second relay, an in-process map joins concurrent attempts, and every relay attempt carries the submission key `docreview:<submissionId>` (as the `Idempotency-Key` header and the `idempotency_key` body field, with an `attempt` counter as metadata) together with the byte-identical message, which Praxis's chat ledger (next section) uses to run the turn at most once. Transport faults (unreachable, connection reset, timeout, 503, and a relay interrupted by a Nexus restart) therefore retry automatically with backoff up to six attempts, and an interrupted relay is retried immediately on boot; a definite rejection (any other 4xx/5xx, or a reply that cannot be saved) is reported and waits for an explicit retry, which resends under the same key. Nothing is relayed before Finish review. The submission state (queued, delivered, failed with or without a scheduled retry, attempts, error, receipt) is shown on the page with a retry action; the page keeps polling while the outcome is open (queued, relaying, or failed with an automatic retry scheduled) and stops only on delivered or a terminal failure.

## Idempotency contract across the seam

Praxis `POST /api/chat` (`src/routes/chat.ts`, ledger in `src/chat-idempotency.ts`) accepts an optional matching header/body idempotency key. A keyed turn must save an atomic, synced `in_progress` claim before any processing. A failed claim answers 503 `idempotency_storage_unavailable` and runs nothing. The exact successful JSON reply is replayable only after its completion record is persisted; receipt-write failure answers 409 `outcome_uncertain`, `retryable: false`, without a success reply. The cache then retains uncertainty; if storage remains unavailable, the previously saved claim is the durable evidence that processing may have occurred. Cache loss, a new boot, handler failure, or a timeout cannot authorize reexecution. An abandoned claim or legacy `failed` record is interpreted as uncertain and blocked. An active claim returns 409 `in_progress`; completion can still arrive from that original handler. Completed keys replay the saved reply with `duplicate: true` and no voice audio. Key reuse with a different fingerprint returns 422; invalid or streaming keyed requests return 400. Ledger read/parse errors fail closed. Records are retained without automatic age/count eviction, since removing a receipt or an uncertain claim permits duplicate processing on a delayed outbox retry. State assumes the existing single supervised Praxis daemon; it is not a distributed lock across simultaneous daemons.

Nexus retries 503 storage refusal and 409 in-progress with the same key. An uncertain outcome is a terminal delivery failure, with the finished submission and all feedback preserved; even explicit retry cannot reexecute it. Resolution requires inspecting the existing conversation/receiver evidence before an operator repairs the ledger; this task adds no automatic replay or approval. Unkeyed bridge chat remains unchanged. Activation remains pending a normal Praxis restart and mechanically finalized cross-executor QA; the repair run does not restart the active daemon or send synthetic feedback to Robert.

## Isolation and verification

Server tests run against a temporary `NEXUS_DB_PATH` with a stubbed Praxis client, so no test turn reaches the live conversation. They cover path boundaries (traversal, symlink escape, wrong extension, missing file), revision capture and change detection, anchor verification, draft persistence, idempotent finish, delivery receipt, retry after outage, duplicate suppression, response-loss recovery, interrupted-relay recovery, no pre-submit delivery, zero-comment finish, and fault injection (a comment save that throws, a finish whose submission insert throws: 500, rollback, feedback preserved, no delivery). A second delivery suite drives the real `relayToPraxis` and `praxisFetch` over 127.0.0.1 against an isolated HTTP receiver that implements the idempotency contract and scripts faults: acceptance followed by response loss, a worker restart before the retry, a process that died mid-relay, and an in-progress 409, each asserting exactly one processed turn, one user row and one reply row. The Praxis side is covered by `tests/chat_idempotency.test.ts` against the real `/api/chat` route with the agent stubbed: replayed reply, response loss after acceptance, 409 while running, ledger survival across a fresh module graph, blocked abandoned and failed turns, claim/receipt storage failures and recovery after cache loss, key reuse, streaming and malformed keys. Dashboard tests mount the viewer with jsdom: GFM rendering, block anchors, HTML/`javascript:` neutralization, tap-to-comment, save states, orphaned anchors, the finish/receipt flow, polling through a scheduled retry, no polling of a terminal failure, finish reconciliation after a lost response and after a rejection, and the phone drawer/composer hand-off. Browser verification runs on an isolated stack (a second `next dev` on :3100 pointed at a throwaway document API on :4100 with a temporary database and a local Praxis stand-in), never against the live document or database. Activation follows the normal supervised restart of the Nexus API child; the dashboard on :3000 is `next dev` and picks the page up on save. The first document is registered against the live registry after activation and verified from the task page and the direct URL at desktop and phone widths.
